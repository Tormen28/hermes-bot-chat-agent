# Changelog

## 0.3.0 - 2026-11-10

**Public name: Hermes Bots.** The display name (`label` in plugin.yaml, Desktop plugin name, README headings, catalog title) is now "Hermes Bots", with a new cover `docs/hermes-bots-030-nous.jpg`. The plugin id and folder remain `bot-chat-agent`, so existing installs, config keys and `hermes plugins update` keep working.

Unified release (everything since the 0.2.0 pin `2bc1ba3`). Box-only build; not pushed, not published.

**New in this cut**

- **Automatic, opt-in panteón.** With the Desktop half on, a Bot Chat request that clearly fits a specialty with no bot gets ONE closing line ("Puedo crear a Daedalus (código) para esto, ¿lo creo?"). On a plain yes the plugin creates the profile (the Desktop half calls the app's stock `profiles.create` / `profiles.configure`; the row appears in the stock Bots panel, titled with the god's name), adds it to `team.assignees` and Hermes hands the request over with `message_agent`; a pending hand-off is reminded at most twice. A no is remembered for 3 days. Optional one-time starter-set suggestion. Never creates without a yes. `/pantheon` stays as an advanced fallback. New module `panteon_auto.py`; `panteon.auto` / `panteon.first_run_suggestion` / `panteon.create_wait_seconds` settings. There is no separate panteón panel.
- **`message_agent` delegations on the status card** (`dm_delegations.py`): `waiting for reply` from the real `post_tool_call` ack, `done` only when a completion notice naming that teammate carries success evidence (exit code 0); failure → `error`; ambiguous → still waiting. Works on v0.23.0/0.23.1, no core change.
- **Memory fix:** the Spanish cue `Decisión:` (with accent) was not recognised, so such decisions were never stored (found in the live two-session run). Verified live: a decision saved in one Bot Chat session is injected in a new, separate one.
- **Public plugin surfaces only (catalog rule 9).** `cron_bridge.py` no longer imports `cron.*` (writes go through the core's `cronjob_manage` tool via `tools.registry`); `context_engine.py` no longer imports `agent.context_compressor` (delegates when reachable, else a small deterministic `LocalCompactor`); profile creation no longer imports `hermes_cli.profiles`. `hermes plugins validate` has no rule-9 warnings and no scanner caution.
- Desktop half: state labels localized in the card (`libre`, `en cola`, `listo`, …); theme-variable colours (works in light and dark themes); panteón request runner + heartbeat.
- **Docs:** README EN/ES rewritten (Desktop half must be switched on in Capabilities → Plugins; panteón; memory; card; honest limits), real screenshots 05–12 from Hermes Webapp v0.23.1 (simulated model, stated), `docs/screenshots/README.md`.

**Carried from the 0.3.0-dev cuts (all included)**

- Guard hardening (R13 evasions, A0.7 injection gaps), agentic short-answer style contract, pending-asks reminder after a mid-turn steer, durable delivery with graceful degradation when the core lacks the durable API (B1 detected by capability, also on the #151935 surface), Windows fixes, strict stability tooling (`tools/stability/runner.py`, `r26_audit.py`), cron bridge, optional context engine (**inactive by default**), generic local memory + `/memoria` (alias `/botmemory`), live status card with multi-bot view, status writer fixes, tests against a release-tarball core.

**Language follows the user; loop-guard explained (new, with tests)**

- Every plugin-written user-facing string follows the language of the user's latest message (es / en / fr / pt / de, offline detection, sticky per session, English fallback; `language: auto` is the new default, an explicit code forces one): status card, `/memoria`, `/botmemory` (the command name no longer decides the language), `/pantheon`. Model-written lines (offer, "ready") get an explicit "answer in <language>" instruction. A yes/no and specialty keywords are recognised in fr / pt / de too.
- Core loop guard refusals (`max_hops` reached, exchange over, duplicate message) now read **stopped** on the card with the reason and what to do, and the tool result carries a note so the coordinator explains it in the user's language instead of retrying.

- Found in the real webapp while checking this (fixed): the Desktop bar stayed in the language of the first page load; a note containing the guard's `[bot-chat-agent]` marker made the bar read "waiting for your OK · {json}" (the note now uses its own marker); and a removed identifier made `StatusBar` throw and the whole card vanish (a static test now guards it). English, French, German and Portuguese users were run end to end with a simulated model; real-model compliance with the "answer in <language>" instruction is not measured.
- Tests: the spawn-contention "work is shared" check depends on the OS scheduler and failed twice on a loaded box; it now gets 3 attempts (exactly-once stays strict on each).

**Found by the full simulated new-user test (fixed, with tests)**

- Install docs: `hermes plugins install /path` does not work on Hermes v0.23 (read as `owner/repo`); README now says `file://` / GitHub shorthand / `--force`, and that the catalog pin may still be 0.2.0.
- **Context engine never compacted.** `update_model()` ran before the lazy compactor existed, so it got `context_length=0` (threshold 0). On a 300-turn run the history grew to 600 messages (~105k tokens on a 64k model). Now the window is remembered. (Engine is still off by default.)
- Memory: `Remember that…` / `Recuerda que…` / `From now on…` (user words only) and fr/pt/de decision cues are stored; an unreadable `memory.db` is moved aside and recreated instead of silently disabling memory forever.
- Status card: a finished delegation stops its clock (it read "done 20m 1s" and kept growing) and leaves the card after 15 min (failures after 1 h).
- Status card is live: elapsed/"stalled" are recomputed on every read (it was frozen between turns); a killed delegate (`exit code -9`) now ends as an error; the card shows at most 4 delegations (open first, then most recent).
- Desktop: `profiles.create` is retried (a brand-new home can answer ENOENT once); polling backs off to once a minute when the Python half is gone (it was a 404 every 3 s after `plugins remove`).
- Uninstall: README says what stays (your data folder, the Desktop half installed by the core).
- Tests: the suite wrote `status.json` into whatever `HERMES_HOME` was set (a live profile); it now uses a temp home. The core-bound Fase 3b gate is skipped with a reason when no core python is configured instead of failing 17 tests.

**Long session, measured with a mock model (300 turns, laptop-class CPU, so only the *difference* means anything):** baseline p50 39 ms / p95 61 ms; plugin p50 63 ms / p95 125 ms (about +24 ms per turn, flat across the run, no growth); plugin + `context.engine: bot-chat` p50 61 ms, requests ~30% smaller than baseline, history bounded. Real-model latency is dominated by the model and is *not* measured.

**Honest limits.** Tests prove mechanism and bounds, not that a real model feels fast in a long Bot Chat (the context engine is off by default). The offer depends on the model following an injected instruction. Screenshots 05–12 use a simulated model.

## 0.3.0-dev (memory) - 2026-11-10

Generic memory for every user, stored only inside Hermes (plugin-local SQLite). No segundo-cerebro, no vault, no API keys.

- **Short-term.** A rolling extractive summary of earlier user/assistant turns (tool payloads skipped) plus the existing pending-asks reminder. Recent messages stay in the core history; the summary is budgeted (`memory.summary_budget_tokens`, default 400).
- **Long-term.** Decisions, project state and lessons live in `<HERMES_HOME>/bot-chat-agent/memory.db`. `pre_llm_call` retrieves only entries that overlap the current request, under `memory.long_term_budget_tokens` (default 400). `post_llm_call` writes back from clear cues in the turn (`Decision:`, `Lesson learned:`, `Decidimos`, `Lección:`, …) with no model and no network. Secret-like text is refused. Oldest rows are pruned past `memory.max_entries`.
- **Config.** `memory.enabled` / `short_term` / `long_term` plus the budgets above (all on by default). Fail-open on a missing, corrupt or unreadable store, and on a v0.23 `post_llm_call` that only passes `session_id` / `turn_id`.
- **Honest limit.** On core v0.23 the hook can only inject a bounded block; it cannot replace the core's growing `conversation_history`. The delegating engine's `select_context` includes the same block when `context.engine: bot-chat` is set. Passing tests and the synthetic bench do not prove live long-session slowness is fixed.
- Benchmark (synthetic long sessions, `tests/_memory_bench.py`) and before/after numbers: `docs/memory-bench.md`. Tests: `tests/test_memory.py`.

## 0.3.0-dev (pending asks) - 2026-11-09

- **Interrupted asks are no longer dropped.** Live test finding: a second user message delivered mid-turn (core steer, `[OUT-OF-BAND USER MESSAGE]`) made the model switch topic and never answer the first ask. New `pending_asks.py`: `pre_llm_call` scans the recent tail of `conversation_history` for earlier real user asks followed by another user message with no final assistant reply, and adds a `[Pending asks]` / `[Pendientes]` block (max 3 asks, 160 chars each, each ask reminded at most twice per session). Pure, fail-open, no I/O. Hook path only (the delegating engine passes no history). `tests/test_pending_asks.py`.

## 0.3.0-dev (hardening) - 2026-11-09

Audit follow-up on the installed 0.3.0-dev (fase5 snapshot `e3b4f60`). No change to the Nous catalog, `main` or PR #3.

- **Guard evasions closed (R13).** New `guard_rules.py`: each command is checked as written, normalised (`/bin/rm`, `\rm`, `env rm`, quote splicing, `sudo`/`nohup` wrappers) and through every recoverable nested payload (`bash|sh|zsh -c`, `cmd /c`, `powershell|pwsh -Command`, `eval`, `$(…)`, backticks, `python -c` literals, inline base64, `-EncodedCommand`). New rules `obfuscated_exec` (decoder piped into a shell/interpreter) and `memory_injection`; `external_sends` now also covers local files leaving through `curl -d @f`, `-F f=@f`, `--post-file`, `| nc`, `scp f user@host:` (loopback allowed). `.env` after `@` is now a secret (`curl -d @.env`). `rd /s` counts as a delete. All regexes are linear and inputs/variants are capped (pathological-input tests included). Corpus: 45 evasions blocked, 73 benign look-alikes allowed (`tests/guard_corpus.py`).
- **A0.7 injection gaps closed (5/5).** `transform_tool_result` wraps tool output with instruction-like text as labelled untrusted data (text preserved); `post_tool_call` flags it and, on cores without that hook, the next turn carries a one-line notice; worker summaries are neutralised in every render path (team note, recently-delivered section, B1 transcript line); writes of standing instructions into `MEMORY.md`/`USER.md`/`SOUL.md`/`AGENTS.md`/memory tools are blocked; `untrusted.py` holds the detectors.
- **Graceful degradation without the durable-delivery API.** Core 0.23.0 has no `ctx.record_delegation_delivery` / `record_completion_note` / `read_session` (verified on the live install). `delivery_path()` reports the live path, a startup log line says which one is active, `has_b1()` no longer raises on a ctx whose attributes explode, and `tests/test_core_compat.py` proves no notification is lost (offer → confirm, cancelled turn re-offers) for `offer`/`auto`/`b1` modes on a v0.23.0-shaped ctx.
- **Windows.** `background_tasks.resource_key` is now platform-neutral (forward slashes, case-folded on Windows), which also fixes the two `KeyError: 'parents'` failures (the serialization key did not match on `\`). Tests that need `fork` or `SIGKILL` skip with an explicit reason on Windows (`tests/_bca_testenv.py`); `tests/test_concurrency_spawn.py` runs real `spawn` contention (4 producers, 4 consumers claiming 600 rows with limit 10) on every platform.
- **Strict stability tooling (`tools/stability/`).** `runner.py` (pass = exit code 0 AND JSON `ok is True`; battery compared by test name against `known_failures.json`; `hermes send` return code checked and recorded; no alerts during the run, one final notification), `live_probe.py` (real core `PluginManager`, throw-away home, full guard corpus through the real hook, p95 limit), `r26_audit.py` (static AST + runtime `sys.addaudithook`: zero network, zero subprocess, zero secret opens, `state.db`/`kanban.db` only `mode=ro`; negative tests prove it detects tampering).
- Manifest declares `transform_tool_result`. Docs: README guard table, `docs/AUDITORIA-LIVE-CORE.md`.

- Fase 3 background work, route A (v1.2 §10, rubric `docs/fase3-rubric.md` v1.0, no core change): background jobs are kanban cards (`kanban_create` to a teammate, or to the user's own worker profile in individual mode — that profile must be listed in `team.gods`); the core dispatcher runs them in another process, the chat turn ends immediately (ACK local p95 4.7 ms over 200 turns, measured offline), and the result returns through the Fase 1 outbox to the origin session. A durable registry (`background_tasks` in `deliveries.db`, schema v3) tracks the real event-driven states — received → queued (`kanban_task_claimed`) → working (`on_kanban_worker_spawned`) → ready (only with a persisted delivery row, no false `listo`), blocked (`kanban_task_blocked`), waiting (derived from an open parent on the board), error (dead-letter), cancelled (plugin-side) — and the turn note renders them (incremental, like the rest of the note). No double dispatch (same idempotency key → one row; the core dedupes by key); no tasks without permission (`kanban_create` to an unlisted profile is blocked); visible queue of 10 open tasks per session (the 11th is blocked with an explicit message); cards on the same resource (same `workspace_path` or `project`) are serialized by merging the open card into `parents`. Cancellation in three levels: response (`/stop` releases offers, the task goes on), task (the chat blocks the card — the guard records a cancel marker, the blocked hook consumes it → `cancelled`, and a later completion is never announced), stop-all (cancels the session's open tasks, keeps everything persisted, blocks new work until the user confirms a resume by retrying the same request in a later turn). Honest limits, documented in the rubric: the core has no `kanban_cancel`, so a cancelled card's worker keeps running until it finishes or blocks (its result stays in `kanban.db`, Bot Chat just does not announce it); timeouts/rate limits are the core's and surface as auto-blocked cards; the desktop bar shows "N resultado(s) listo(s)" from kanban events observed while the app is running (deduplicated by task id, never naming a session it cannot prove), but it cannot query the outbox without the Q5 gateway RPC (design-only proposal, not implemented), so counts reset on reload and the ≤1 s bar latency is not measurable offline (Fase 5). Gate (level A, offline, `tests/test_fase3_gate.py` 23 tests + `tests/test_fase3_desktop.mjs` 10 node tests): turn never waits for the worker, states only move on real events, no false ready, no double dispatch, queue/permission/serialization enforced, three cancellation levels, stop-all resumable; full battery 152 tests, 147 OK + the same 5 expected A0.7 failures; gates 1a 9/9, 1b 17/17, 2 16/16. Bugs found and fixed while gating: (1) the json revert path skipped the delivery write in the new note functions; (2) the cancel hint pushed the A0.8 case-B note over 1,400 chars, so it now only renders when there is open work to cancel; (3) `background_tasks` ordered by a nonexistent `id` column; (4) a same-status update could overwrite the first delivery id with a late duplicate's.
